## Concrete proposed change

Only the existing quad call in `Scene::finish` is replaced:

```rust,ignore
self.quads.sort_by_key(|quad| quad.order);
```

It calls a private `sort_quads_by_order` helper with private reusable
`QuadOrderScratch`. `Scene` gains that private scratch field, which defaults to
empty. The unified diff removes exactly the one quad-comparator source line;
all existing shadow, path, underline, surface and three sprite comparators stay
byte-for-byte unchanged. Paint operations, draw-order assignment, clipping,
layers, atlas texture grouping, public methods and dependencies are unchanged.

The proposed helper has three paths:

1. **Already ordered:** scan once, return without changing quads or allocating.
2. **Stable counting:** count each order, turn counts into prefix positions,
   assign each original input a unique destination in input order, then apply
   that permutation with safe whole-quad swaps.
3. **Stock:** keep `sort_by_key(|quad| quad.order)` when counts would be sparse,
   overflow, exceed policy limits, or cannot reserve bounded scratch storage.

Stable ties follow directly from assigning destinations while iterating original
input order. Every destination is a distinct number in `0..len`; swapping both
the quad and its destination until each is fixed applies that permutation.
The implementation reads only `quad.order` and swaps complete `Quad` values.
It reconstructs no payload, performs no float arithmetic, and uses no unsafe code.

### Scratch and fallback policy

- At most **65,536 count bins**; at most **four bins per input quad**.
- At most **1,048,576 bytes of retained element capacity** across two
  `Vec<usize>` buffers: counts and destinations. Checked arithmetic is used for
  order conversion, bin count, density and byte calculation.
- Indices are `usize`, avoiding unchecked narrowing of quad indices to `u32`.
- When either buffer must grow, both old buffers are dropped before reservations.
  This prevents independently retained high-water capacities from exceeding the
  combined limit. Reservation errors release scratch and take the stock path.
  Actual granted capacities are checked, since `try_reserve_exact` may grant more
  than requested. Counts and destinations are cleared/reinitialized before reuse.
- Sparse or `u32::MAX` unsorted cases take stock sorting without allocating an
  enormous count table. Already-sorted sparse/max-order input needs no table.
- This is a bound on **additional retained vector element storage**, not process
  RSS, allocator metadata, allocator-internal temporary allocation, or the stock
  sort's own allocation. A reservation can transiently receive excess allocator
  capacity before its post-reservation check releases it. No hard OS memory cap
  or recovery from an allocator abort is claimed.

The limits are conservative proposed resource policy, not measured optimization
thresholds. Approval may choose different limits, which changes the patch hash
and requires another review.

## Costs, risks and fallback

Counting takes `O(n + bins)` work and `O(n + bins)` supplementary integer storage.
It scans, fills count/index arrays, and swaps at most `n - 1` times. Swapping
large quads still moves payload bytes. The stock stable sort can already exploit
ordered runs; this proposal may regress short, partly sorted or sparse workloads.
Two buffers per live Scene keep capacity until Scene drop or an over-budget/
stock-path release; `Scene::clear` itself retains scratch. Many windows/scenes can
therefore multiply the per-scene storage limit. Initial/default Scene size also
grows by two Vec headers.

The complete accepted fallback is the existing stable sort. It is used in the
helper's stock paths and remains the differential oracle. Restoring the accepted
unpatched package disables the candidate completely. No runtime environment
override, new Cargo feature or global optimization configuration is introduced.
An isolated stock-control build may use the original source snapshot for paired
evaluation; it must not silently alter active RustUI.

Incorrect tie order can alter translucent blending. Counting-index bugs can
permute unrelated geometry even while counts remain correct. Stale scratch can
surface after scene shrink/clear. The tests and native checks below target those
risks; model success does not remove them.

## Executed independent Python differential model

An in-memory standard-library model of destination assignment and swap cycles
was compared against Python's stable `sorted(key=order)`, including whole symbolic
payload tuples and original indices. Seed `0x51554144`; lengths
`0,1,2,3,4,8,16,31,64,257,1024`; 100 repetitions each; dense random, reverse,
sorted and sparse/maximum-order inputs; budgets `0,64,1048576` bytes. Checked
planning boundaries were separately exercised for 32- and 64-bit word sizes.

**13,200 cases passed:** 6,147 already-ordered, 1,946 counting, 5,107 stock.
The report is `target/headstart/quad-sort-proposal-model.json`, bound to the
proposal patch hash. It also records that the sole removed existing source line
is the quad `sort_by_key` call. This tests the model and proposal text; it is not
Rust, allocator-failure, GPUI, native, pixel or performance acceptance.

The core model is reproducible without importing the proposed Rust source:

```python
def counting_permutation(items, bins):
    result = list(items)  # each item: (order, original_index, complete_payload)
    counts = [0] * bins
    for order, _, _ in result:
        counts[order] += 1
    start = 0
    for order, count in enumerate(counts):
        counts[order] = start
        start += count
    destinations = []
    for order, _, _ in result:
        destinations.append(counts[order])
        counts[order] += 1
    for index in range(len(result)):
        while destinations[index] != index:
            other = destinations[index]
            result[index], result[other] = result[other], result[index]
            destinations[index], destinations[other] = destinations[other], destinations[index]
    assert destinations == list(range(len(result)))
    assert result == sorted(items, key=lambda item: item[0])
    return result
```
