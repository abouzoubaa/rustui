# Implementation: G0–G5 as patches

## Short answer

G0 to G3 and G5 need 10 patches on the vendored GPUI Fast 0.1.14 crates, plus 1 change to RustUI's patch script. G4 needs no GPUI patch: GPUI Fast already has a public API for extra layers. Read from RustUI branch `codex/fa-0-safety` (6a0592f0, Nov 20) and GPUI Fast `main` (2002081).

Reading the code changed four things in the plan:

1. **The G2/G3 planner should come from GPUI Fast, not Havunen.** GPUI Fast `main` (0.2.2, newer than RustUI's 0.1.14) has `crates/gpui_windows/src/fast/partial.rs`: a damage planner written for GPUI Fast's own scene. It already handles what Havunen's tile hash does not know about: atlas tiles uploaded again, dynamic textures, up to 8 damage rectangles, and the scroll shift (G3) in the same function. About 830 of its 1,541 lines are platform-free Rust. Havunen's PR still gives the Metal side: kept texture, copy pass, clear of the damaged area, frame modes and memory budget.
2. **G4 is RustUI code only.** `Window::enable_window_composition()`, `WindowComposition::create_gpui_surface()` and `Window::with_composition_surface()` are public in GPUI Fast 0.1.14. Each extra GPUI layer gets its own `MetalRenderer`, so G1 and G2 work on it with no extra code.
3. **The patch script cannot add new files today.** `scripts/apply_f0_fast_candidate_patch.py` refuses a target that does not exist. G patches add new files, so the script needs one small change first.
4. **GPUI Fast warns that this may not pay on a fast GPU.** Its own planner turns itself on only for software drawing: "on a GPU a whole frame costs less than the comparison saves" (its comment). That is about speed on Windows. On a Mac the goal is power and battery, so G0 must measure GPU time and energy before G2 and G3 are switched on by default.

## How a G patch is made in RustUI

Every G patch follows the same pattern as the 21 patches already in `patches/candidate-kit-fast/core-stack.json`. Nothing in `vendor/` is edited by hand.

1. **Source:** Cargo reads crates from `vendor/` (`.cargo/config.toml` replaces crates.io with `vendored-sources`). GPUI Fast lives in `vendor/gpui-fast-0.1.14`, `vendor/gpui-fast-apple-0.1.14`, `vendor/gpui-fast-macos-0.1.14` and siblings.
2. **Patch file:** a `git diff` of the vendored files, saved as `patches/candidate-kit-fast/<name>.patch`.
3. **Checksum file:** the same patch also updates the crate's `.cargo-checksum.json`, so Cargo accepts the changed sources. Every existing manifest lists it as a target.
4. **Manifest:** `patches/candidate-kit-fast/<name>.json` with `patch_sha256` and, per file, `pre_sha256` and `post_sha256`.
5. **Replay:** `python3 scripts/apply_f0_fast_candidate_patch.py <manifest> --check | --apply | --reverse`. It refuses unknown file states, applies in a temporary copy, checks the result hashes, and proves the reverse gives back the exact original.
6. **Stack:** an ordered list of manifests. The G patches go in a new `patches/candidate-kit-fast/damage-stack.json`, applied after `core-stack.json`.

**The one gap.** `apply_f0_fast_candidate_patch.py` stops with "missing or non-regular target" when a file does not exist. G patches add new files such as `src/fast/damage/plan.rs`. Ticket G-T0 adds this rule: a manifest entry with `"pre_sha256": null` means "the file must be absent before, and is created"; on `--reverse` it is deleted. The "reverse gives the exact original" check stays, now including "file absent". `scripts/check_f0_fast_core_stack.py` reads one fixed stack path; G-T0 also gives it a `--stack` argument.

**Where new code goes.** Following GPUI Fast's own rule (its `fast/` folders, checked by its `script/check-upstream`): new logic in new files under `src/fast/damage/`, and upstream files get only small calls into it. This keeps each patch to the vendored upstream files short, and easy to rebase when GPUI Fast moves from 0.1.14.

## G0 and G1 in code

The code blocks in this tab are sketches of the shape, not final code: names follow the vendored files, but Codex writes and compiles the real code ticket by ticket.

### G0 — measure first (patch 1)

RustUI already has a frame recorder: core patches `gpui-frame-recorder-v1-fast` and `gpui-frame-phases-v1-fast` print `RUSTUI_FRAME_LOG {...}` lines when `RUSTUI_FRAME_LOG=1`. They time the CPU only. Patch 1 adds the GPU side in the same format, so existing scripts can read it.

In `MetalRenderer::draw`, after the command buffer exists and before `commit`:

```rust
// Apple metal_renderer.rs, draw(): one added call
crate::fast::damage::metrics::on_commit(&command_buffer, frame_mode_label);
```

```rust
// Apple src/fast/damage/metrics.rs (new)
pub(crate) fn on_commit(buffer: &ProtocolObject<dyn MTLCommandBuffer>, mode: &'static str) {
    if !enabled() { return; }               // reads RUSTUI_FRAME_LOG once, like the core recorder
    let block = RcBlock::new(move |buffer: NonNull<ProtocolObject<dyn MTLCommandBuffer>>| {
        let buffer = unsafe { buffer.as_ref() };
        let gpu_ms = (buffer.GPUEndTime() - buffer.GPUStartTime()) * 1000.0;
        eprintln!("RUSTUI_FRAME_LOG {{\"event\":\"gpu\",\"mode\":\"{mode}\",\"gpu_ms\":{gpu_ms:.4}}}");
    });
    unsafe { buffer.addCompletedHandler(RcBlock::as_ptr(&block)) };
}
```

Until patch 5 lands, `mode` is always `"full"`. Afterwards it is `skip`, `copy`, `partial`, `shift`, `retained` or `direct`, and a skipped frame logs one line with no GPU time.

**Energy.** GPU milliseconds do not equal battery. Each G0 benchmark scene also runs 60 s under `sudo powermetrics --samplers gpu_power,cpu_power -i 1000`, with the average power recorded. The 5 scenes: idle window with a blinking caret; typing in the 10,000-line editor; mouse sweeping over list rows; an auto-scrolling log adding 10 lines a second; a card dragged across a board.

### G1 — skip or copy an identical frame (patches 2 and 5)

The renderer can see that a scene equals the last one, but not why GPUI is presenting. Patch 2 passes that reason down, in a new core file:

```rust
// Core src/fast/present_hint.rs (new)
thread_local! { static REQUIRED: Cell<bool> = const { Cell::new(true) }; }

pub(crate) fn set(required: bool) { REQUIRED.with(|r| r.set(required)); }

/// Whether the frame being presented must reach the screen even if it looks
/// like the last one: the keepalive after fast input, or a present the
/// system asked for. `true` outside a frame request, so the safe answer.
pub fn fast_present_required() -> bool { REQUIRED.with(Cell::get) }
```

```rust
// Core window.rs, frame request closure, right after high_rate_input is computed
crate::fast::present_hint::set(request_frame_options.require_presentation || high_rate_input);
```

Patch 5 uses it in `MetalRenderer::draw`. The plan is made before a drawable is taken, so a skipped frame never touches one:

```rust
// Apple metal_renderer.rs, draw(), at the top (patch 5)
let size = drawable_size(&layer);                       // layer.drawableSize()
let mode = crate::fast::damage::frame::choose(self, scene, size);
let mode = match mode {
    FrameMode::Same if !gpui::fast_present_required() => {
        crate::fast::damage::metrics::skipped();
        return;                                          // drawable stays unused
    }
    FrameMode::Same => FrameMode::Copy,                  // keepalive: show the kept texture
    other => other,
};
// ...existing drawable code, then crate::fast::damage::frame::render(self, scene, mode, ...)
```

Why `return` is safe: with a `CAMetalDisplayLink`, `metal_frame` in macOS `window.rs` already treats an unused drawable as "no draw, no present" and pauses the link when GPUI did not ask for another frame. On macOS 13 (no display link), `nextDrawable` is simply never called. The screen keeps the last presented image either way.

## G2 and G3 in code

G2 has two halves: a planner that says what changed (patch 4), and a Metal frame that redraws only that (patch 5). G3 adds one more planner answer, "it only moved", and one copy (patch 8).

### The planner (patch 4): port GPUI Fast's `partial.rs`

`partial.rs` reduces every primitive to a **signature**: what it looks like apart from where it is (a hash of colour, size, corners, border, atlas tile, transform), plus its bounds, its clip and the area it can touch. `plan(old, new, view)` pairs this frame's signatures with the last frame's and returns `Plan { shift, damage }`: up to 8 rectangles to redraw, and optionally one area to copy moved. It returns `None` (draw whole) when damage passes 60% of the window or draw orders of unchanged primitives disagree.

| Part of `partial.rs` | Lines | In `damage/plan.rs` |
| --- | --- | --- |
| Constants `MAX_DAMAGE` 0.6, `MAX_RECTS` 8, `MAX_MERGED` 64, `MIN_MOVED` 4, `SAME` | 89–97 | Copy as is |
| `wanted()` (Windows software-adapter check) | 103 | Drop; RustUI's switch replaces it |
| `Uploads` (tiles uploaded since last frame) | 122–145 | Copy; filled by `metal_atlas.rs` |
| `Area`, `Sig`, `Key`, `sig`, `transformed` | 162–437 | Copy; drop `Area::rect` (Windows `RECT`) |
| `signatures(scene, uploaded, dynamic)` | 439–584 | Copy; rounded clip groups via Apple's own `crate::fast::rounded_clip::group` (private today, made pub(crate)), same idea as Windows |
| `Plan`, `plan`, `tidy`, `orders_agree`, `shape`, `coarse` | 591–892 | Copy as is |
| `Drawer`, `Scissor`, `Canvas`, `Partial` (Direct3D) | 893–end | Drop; Metal side is patch 5 |
| Tests | end of file | Copy the planner tests (from line 1281: plan, orders\_agree, signatures); drop the Direct3D ones |

Inputs from the Metal side (`damage/inputs.rs`):

- **Uploaded tiles:** `MetalAtlas::upload` records `(texture_id, tile_id)`; `remove` and texture clears set `lost`, which forces a whole draw. Same contract as Windows `DirectXAtlas::take_uploads`.
- **Dynamic textures:** `|id| gpui::DynamicTextureId::from_atlas_texture_id(id).is_some()`; their sprites are always fresh, as on Windows.
- **Scroll layer tiles:** `signatures` returns `None` for any scene with scroll layer tiles, because tiles change under unchanged sprites. Patch 7 lifts this (below).

### The Metal frame (patch 5)

State kept per `MetalRenderer`, in `damage/retained.rs`: the kept texture (BGRA8, `Private` storage, render target and shader read), its size, whether it is valid, last frame's signatures, and a memory reservation. The budget is Havunen's: 64 MB per GPU device shared by all windows and layers (two 4K targets); over budget means whole draws, never failure.

`frame::choose` picks one mode, in this order:

1. `RUSTUI_DAMAGE=0`, or `presents_with_transaction` (live resize) → **Direct**: today's path, kept texture marked invalid.
2. Size, scale, transparency or atlas `lost` changed → **Retained**: whole draw into the kept texture, then copy.
3. `signatures` or `plan` says "draw whole" → **Retained**, or **Direct** if the previous frame was also whole (Havunen's rule: a run of big changes skips the copy).
4. Plan with no damage and no shift → **Same** (G1: Skip or Copy).
5. Otherwise → **Partial** (damage, optional shift).

`frame::render` per mode:

| Mode | Command buffer contents |
| --- | --- |
| Direct | `render_frame(drawable)` as today |
| Retained | `render_frame(kept)`, then copy pass kept → drawable |
| Partial | \[shift blit, G3\] → clear pass on the damage box → `render_frame(kept)` with Load + scissor → copy pass kept → drawable |
| Copy | copy pass kept → drawable only |
| Same + not required | nothing: `draw` returned early |

**One hook covers every main pass.** GPUI Fast restarts the main pass in three places (`metal_renderer.rs`, `fast/paths.rs`, `fast/rounded_clip.rs`), all through `new_command_encoder_for_texture`. Scroll tiles and path textures also go through it, but with other target textures. So the hook compares the target with the frame's partial target:

```rust
// Apple metal_renderer.rs, new_command_encoder_for_texture (patch 5): two added calls
let clear_color = crate::fast::damage::frame::pass_clear(texture, clear_color); // None (Load) on the partial target
// ...existing descriptor + encoder code...
crate::fast::damage::frame::pass_scissor(texture, &command_encoder);          // setScissorRect on the partial target
```

`frame::render` sets a thread-local "partial target = this texture, box = this rectangle" before `render_frame` and clears it after.

**V1 draws one box.** `plan` returns up to 8 rectangles; patch 5 draws their bounding box with one scissor. Drawing each rectangle separately means encoding every batch once per rectangle; add it only if G0 shows two distant changes (caret plus clock) are common.

**The three shader functions (patch 3),** added to `shaders.metal`; with RustUI's `runtime_shaders` feature they are compiled at startup with the rest:

```metal
struct DamageCopyOut { float4 position [[position]]; };

vertex DamageCopyOut damage_fullscreen_vertex(uint id [[vertex_id]]) {
    float2 p = float2((id << 1) & 2, id & 2);                 // one triangle covering the target
    return { float4(p * float2(2, -2) + float2(-1, 1), 0, 1) };
}

fragment float4 damage_copy_fragment(DamageCopyOut in [[stage_in]],
                                     texture2d<float> kept [[texture(0)]]) {
    return kept.read(uint2(in.position.xy));                    // exact pixel, no filtering
}

fragment float4 damage_clear_fragment(constant float4 &color [[buffer(0)]]) {
    return color;                                               // used with a scissor
}
```

The copy is a render pass, not a blit, because release drawables are `framebufferOnly` (`configure_layer`): a blit cannot write them, a render pass can. Both pipelines use no blending.

### G3 — scroll shift (patch 8)

`plan` already detects it: 4 or more primitives of the same look moved by one whole number of pixels vertically inside one clip, with draw orders agreeing. Patch 8 only adds the copy, at the start of the Partial command buffer:

1. Blit `from` (the clip's old pixels) from the kept texture into a scratch texture of that size, kept between frames.
2. Blit the scratch texture into `to` (the same size, moved) in the kept texture. Two steps, because a blit with overlapping source and destination in one texture is not allowed.
3. Then the normal Partial steps redraw the exposed strip and anything that did not move.

Example: a log panel 600 × 800 px scrolls up 20 px. The blits move 600 × 780 px; the redraw box is 600 × 20 px plus the scrollbar thumb.

### Scroll layers (patch 7)

RustUI uses GPUI Fast scroll layers, and `signatures` gives up on any frame that has them. The reason is that a tile can be redrawn while its sprite stays the same. The fix uses what the tile cache already knows:

1. Move `rasterize_tiles` from `render_frame` to the top of `MetalRenderer::draw`, before planning. It already commits its own command buffer, so its order with the frame does not change. `render_frame` skips it when it already ran this frame.
2. Make it return the tiles it rasterized (`planned`).
3. In `signatures`, a tile sprite is fresh when its tile is in that list, like an uploaded atlas tile. Remove the "scroll layers mean `None`" rule. A cache `clear()` (on failure) sets `lost`.

Then a scroll-layer scroll looks like moved sprites, and G3 can even use the shift.

### Proof (patch 6 and tests)

- **`RUSTUI_DAMAGE=verify`:** after each non-Direct frame, `damage/verify.rs` also draws the same scene whole into a second texture, blits both into shared buffers, and compares them in the command buffer's completion handler. The first mismatch logs `RUSTUI_FRAME_LOG {"event":"damage_mismatch","mode":...,"x":...,"y":...}` and turns damage off for that window. Slow; debug and owner checks only.
- **Headless pixel tests** use the existing `MetalHeadlessRenderer` (`render_scene_to_image`, test-support). A test-only entry draws scene A, then scene B through the chosen mode into the kept texture, reads it back, and compares it byte for byte with B drawn whole. Every test asserts the mode it expected (Partial, Shift, Copy), so a test cannot pass by quietly drawing whole.
- **Magenta pre-fill** (Finityno's idea): in tests, the damage box is filled with magenta before redrawing, so a pixel the redraw forgot shows as magenta.
- **Planner tests** come with the port from `partial.rs`.
- **Native check:** the Playground pixel oracle from F0-13 (Swift capture, `apps/rustui-playground`) runs the 5 G0 scenes with damage on and off and compares captures.

### Per option

- **`DragStyle::Floating`.** GPUI already paints the drag element on the overlay surface (core `window.rs` \~4250). But the base and overlay only become separate layers when the tree holds more than 2 surfaces (`splits`, line 767). So at drag start RustUI creates one empty GPUI surface placed above the overlay; that makes the window split. The base layer is then unchanged during the drag and G1 skips it; the empty layer is unchanged too and is skipped. At drop, RustUI removes the surface.
- **`DragStyle::InPlace`, move in place.** Pure component logic: the board keeps A in its child list at its own position and z-order, and changes only A's offset each frame. No composition call. G2 redraws A's old and new spots, with B painted over A in paint order.
- **`DragStyle::InPlace`, layer sandwich.** The board makes two layers, `moving` and `above`, placed above the base and below the overlay. When painting its children it does:

```rust
// crates/rustui board paint (sketch)
for child in &children[..a] { child.paint(window, cx); }               // base layer
window.with_composition_surface(moving, |w| a_child.paint(w, cx))?;    // A alone
window.with_composition_surface(above, |w| {
    for child in &children[a + 1..] { child.paint(w, cx); }            // B and the rest
})?;
```

- **`LayerHint::Promote` / `Auto`.** Same idea with one layer: while the animation runs, the element paints inside `with_composition_surface(promoted, ...)`; the base no longer changes, so G1 skips it.

### Limits found in the code

- **Creating a layer is not free.** A new GPUI layer builds a `MetalRenderer` through `new_internal`, which, with RustUI's `runtime_shaders` feature, compiles the Metal shader library from source again. Creating layers at drag start can stutter the first frame. RustUI should create a window's G4 layers once, when the window opens or at first idle, and keep them. An unchanged empty layer then costs nothing per frame thanks to G1. If startup cost matters, a later patch can let `new_sharing_atlas` reuse the base renderer's pipelines.
- **Create layers outside paint.** `create_gpui_surface` and `remove_surface` reorder platform views. Call them from event handlers or `cx.defer`, not during prepaint or paint.
- **Inside a scroll layer, layer switching is ignored.** `with_composition_surface` paints "where the layer does" when inside a scroll layer (its doc comment, line 1250). A board inside a GPUI Fast scroll container falls back to move in place. It still looks right, just without the zero-redraw gain.
- **The sandwich only works when the board is the last thing painted in its area.** Anything painted after the board on the base layer, overlapping it, would end up below `moving` and `above`. So the sandwich is opt-in per board (`.top_most_in_area(true)`); otherwise RustUI uses move in place.
- **Layers present separately.** Each `CAMetalLayer` presents its own drawable. In one frame, the base and a moving layer can show one frame apart. This is the same as GPUI Fast's existing overlay layer; check it in the drag benchmark.

## Risks found in the code

- **The gain may be small on Apple GPUs.** GPUI Fast enables its own planner only for software drawing, because on a GPU a whole frame cost less than the comparison. Apple GPUs draw in tiles and are fast at whole UI frames. Partial redraw adds the copy pass, a full-window read and write, to every non-skipped frame. G0 decides with GPU time and power, and G2-6 can keep only G1 (Skip and Copy) if Partial does not pay.
- **CPU cost of signatures.** `signatures` walks every primitive every frame, and `plan` builds hash maps. On a 5,000-row list this is real work; G0 must log it next to the CPU phase times RustUI already records.
- **Version gap.** `partial.rs` is from GPUI Fast 0.2.2; RustUI is on 0.1.14. Every `Scene` field and method that `signatures` reads (`len`, `layers.frames[].tile_size`, quad `border_style`, shadow `element_bounds` and `inset`, sprite `transformation`, polychrome `grayscale` and `opacity`, underline `wavy`, path vertices) exists in the vendored 0.1.14 core, checked one by one. Codex must still compile the port against 0.1.14. When RustUI moves to a newer GPUI Fast, check first whether upstream added a Metal planner.
- **Scroll layer change is the riskiest patch (7).** It moves `rasterize_tiles` earlier in the frame. Keep it last among the G2 patches, behind its own check, with the scroll pixel tests from F0-14 run before and after.
- **Layer creation stutter (G4).** Each new GPUI layer compiles the shader library again under `runtime_shaders`. Create layers once per window, never at drag start.
- **Live resize.** `presents_with_transaction` always takes the Direct path, so resizing gets no gain and no risk.
- **Transparent windows.** The clear pass must write the same clear colour and alpha that `draw_primitives_to_texture` uses (`alpha = if opaque { 1 } else { 0 }`); a translucent-window pixel test is part of G2-4.
