# RustUI Performance Merge Plan: GPUI Forks and Damage Tracking

Nov 19, 2026 · @Adil Bouzoubaa

## Short answer

Don't merge all the forks. Take GPUI Fast as the base (it already does the CPU half), then add one GPU-side layer on top of it: Havunen's tile-hash damage planner, ported to GPUI Fast's Metal renderer.

A frame costs two things: building it on the CPU (views, layout, paint) and drawing it on the GPU (every pixel of the window). GPUI Fast solves the first: it reuses unchanged views, layout and text, and scrolls with cached tiles. It does **not** solve the second on macOS: its Metal renderer still clears and redraws the whole window every frame. That gap is exactly RustUI Stage G.

The merge, in one line per piece:

1. **Base:** GPUI Fast (retained views, scroll layers, bounds grid, path cache). Do not re-implement any of it.
2. **Present skip:** when the new frame equals the old one, don't draw or present at all (Zed PR #62455 idea).
3. **Partial redraw:** hash the scene per 64 px tile, redraw only the box around changed tiles into a kept texture, copy it to the screen (Havunen gpui-ce PR #29 code).
4. **Scroll shift:** when content only moved by whole pixels inside one clip, copy the old pixels shifted and draw only the new strip (GPUI Fast's own Windows WARP code, moved to Metal). This is what makes append-only log and chat panels cheap.
5. **Drag:** draw the dragged item on GPUI Fast's existing overlay surface (window composition), so the base window does not redraw while dragging. This replaces the plan to build a separate wgpu surface by hand.
6. **Proof:** every partial frame must be byte-identical to a full redraw, checked by tests and by a runtime verify switch.

Everything else (Zed's Linux path, Finityno's animation-only path, Hexpy's glass rules, Cap's patch, the damage-rects crate, the wgpu pipeline cache) is either covered by the pieces above or is for later platforms.

## Where RustUI is today

RustUI 0.4.0 runs on gpui-pre 0.3.12 with GPUI Kit 0.9.1, and every frame is drawn in full. The facts this plan builds on, read from `main` at commit 925436b5 (Nov 13, 2026):

| Metal renderer | Clears the target (`MTLLoadAction::Clear`) and redraws the whole scene every frame; no kept texture, no damage | `vendor/gpui-pre-apple-0.3.12/src/metal_renderer.rs` |
| Scene reuse | Already exists on the CPU side: `Scene::replay` copies paint operations of cached views from the last frame | `vendor/gpui-pre-0.3.12/src/scene.rs` |
| Live resize | Switches to synchronous presents (`set_presents_with_transaction(true)`) | `vendor/gpui-pre-macos-0.3.12/src/window.rs` |

Second, building damage tracking on gpui-pre and then moving to GPUI Fast would mean writing the Metal patch twice; it should be written once, on GPUI Fast.

## What each source does

Eight sources, two kinds of work: four cut CPU frame building, five cut GPU pixel drawing (GPUI Fast does both). The GPU ones differ mainly in how they decide what changed and how they keep the old pixels.

### CPU side

- **GPUI Fast — retained views** ([architecture](https://github.com/longbridge/gpui-fast/blob/main/docs/architecture.md)). Every view becomes a cached subtree keyed by `GlobalElementId`. Each view records what it read (entities, globals, window input); unchanged views copy last frame's output, changed nested views are spliced in. Layout nodes stay in Taffy across frames; text measurements are kept. Proven by an oracle test: an incremental window and a from-scratch window must produce the same scene every frame. Measured: idle 60 panels 3.31 → 0.19 ms. Rule for apps: state read outside tracked entities needs `cx.notify()`.
- **GPUI Fast — scroll layers.** A scrolled container is painted once (viewport plus 2 viewports of overscan) into 64 MB-capped GPU tiles; offset-only frames composite tiles as sprites. Only when the viewport lies on one opaque solid quad. Lists (`uniform_list`, `list`) have layers **off** for now.
- **GPUI Fast — other kept work.** A uniform grid replaces upstream's R-tree for draw ordering, and orderings of reused views are replayed. Path tessellation cache (2048 shapes, 16 MiB). Glyph runs computed once per run.
- **Cap `zed-perf.patch`** ([PR #3887](https://github.com/CapSoftware/Cap/pull/3887)). A balanced R-tree for ordering, scene sort that moves each primitive once, cheaper text painting. Up to −56% on `primitives_8192` (M4). Mostly overlaps GPUI Fast's grid and glyph work.

### GPU side

- **Havunen gpui-ce PR #29** ([PR](https://github.com/Havunen/gpui-ce/pull/29)). The most complete design, on Metal, D3D11 and wgpu. Per frame it hashes everything painted into each **64 px tile**, in paint order, leaving out the global draw order (so a hover highlight that renumbers rows does not mark them changed). The bounding box of changed tiles is redrawn; over half the window means full redraw. Pixels are kept in a **separate retained texture**, then copied to the drawable — this avoids needing the drawable's age. Four frame modes: Direct, Retained, Partial(box), Copy. A run of large changes goes Direct to skip the copy. Retained memory is budgeted per device (two 4K targets). Atlas changes, filters, surfaces and synchronous presents force full redraw. Measured in GitComet: history scroll on DX12 25.9% → 10.8% app GPU.
- **Zed PR #62455** ([PR](https://github.com/zed-industries/zed/pull/62455)). Three experimental flags: `PRESENT_SKIP` (identical frame → no present; \~7x less GPU), `ORDER_TOLERANT_DAMAGE` (ignore absolute order numbers), `PARTIAL_RENDER` (copy previous frame, clear damage rects, one scissored draw per rect; \~4x less GPU while typing). Linux only.
- **Hexpy gpui-ce PR #11** ([PR](https://github.com/Hexpy-Games/gpui-ce/pull/11)). Diffs scenes by trimming the common prefix and suffix of hashed paint operations. Extends damage through blur, scale and motion groups. Partial only when the damage is ≤ ¼ of the target and no atlas tile was removed since the kept frame. Test: a change under glass must be byte-identical to a full render.
- **Finityno zed PR #86** ([PR](https://github.com/Finityno/zed/pull/86)). Metal only, and only for frames where just time animations advanced (spinner, shimmer). Up to 8 rects, merged within 16 px, cut off above half the viewport; blur grows the rect to the whole blur. Synthetic: 1.785 → 0.196 ms GPU per present. Test trick: pre-fill damaged pixels with magenta so a wrong copy shows up.
- **GPUI Fast — Windows WARP partial redraw** (`crates/gpui_windows/src/fast/partial.rs`). Compares primitive *signatures* across frames. Detects a **scroll**: same primitives moved by a whole number of pixels vertically in one clip → copies those pixels shifted and redraws only the exposed strip. Atlas re-uploads mark sprites changed. Software adapters only; \~100 → \~19 ms a scrolled frame.
- **GPUI Fast — window composition.** The scene is split onto ordered surfaces: base, native views, then an **overlay** surface for deferred draws, tooltips, prompts and the **active drag** element. On macOS each surface is its own layer. The overlay surface is only split off when a native surface exists.

### Small items

- **kunkka gpui-ce pipeline cache:** wgpu pipeline cache, window open 130 → 2 ms after the first. wgpu only.
- **damage-rects crate:** collects dirty rectangles and merges them; no GPU or GPUI tie-in.

## How each step works

Each step answers one plain question: is the picture the same (G1), which part changed (G2), did it only move (G3), and can the moving part live on its own layer (G4).

### G1 — Skip or copy an identical frame

GPUI does not redraw for no reason, but it does send the same picture again in two common cases:

- **The 1-second keepalive.** After fast input (about 6 or more events in 100 ms: moving the mouse, scrolling, quick typing), GPUI keeps presenting on every screen refresh for 1 more second, even when nothing changed. This is normal upstream GPUI code (`InputRateTracker`, `Duration::from_secs(1)`), also in GPUI Fast and gpui-ce. Each of these presents redraws the whole window on the GPU. Example: sweeping the mouse over a toolbar with no hover effects gives about 120 full redraws of the same picture.
- **`cx.notify()` with no visible change.** A hover state with no hover style, a timer updating a value that is not shown. The scene is rebuilt and the pixels are the same. Zed measured this case: skipping it cut GPU use by about 7x.

G1 compares the new scene's fingerprint with the last one. It has two modes:

- **Copy** during the keepalive: present the kept texture instead of drawing again. The screen stays fast, the GPU barely works.
- **Skip** in all other cases: no draw, no present.

Copy needs the kept texture from G2, so G1 and G2 are built together.

**Why the keepalive exists — ProMotion.** ProMotion is not a monitor. It is Apple's name for a screen that changes its own refresh speed: 120 times a second when things move, much slower when nothing changes, to save battery. MacBook Pro 14" and 16" (2021 and later) have it, as do some iPhones and iPads. The screen decides its speed by watching how often the app sends pictures. GPUI's keepalive keeps sending pictures so the screen stays fast while you are still moving.

**The first-frame problem.** After the app sits still for a few seconds, the screen slows down. When you then press a key, that first picture waits for the slow screen and appears a little late. The keepalive cannot fix this: it starts after the input arrives, when the screen is already slow. G1 does not fix it either; it only makes the keepalive cheap.

The real fix is to tell macOS what RustUI wants. On macOS 14+, RustUI paces frames with a `CAMetalDisplayLink`, which has a `preferredFrameRateRange` setting. RustUI does not set it today, and neither does GPUI Fast. A small patch asks for 120 Hz when input starts and resets it when the app goes quiet. macOS keeps the last word, so the first keypress after a long pause may still be slightly late; only a test on a ProMotion MacBook shows how much this helps.

### G2 — Redraw only the part that changed

There are two separate questions:

- **Which components rebuild (CPU):** GPUI Fast already answers this, by tracking what each view reads.
- **Which pixels redraw (GPU):** this is G2. It works on what was painted, not on components.

Each 64 px tile gets a fingerprint of everything painted into it: quads, text, icons, shadows. If a tile's fingerprint changed, the tile is dirty. Overlaps are handled by how the redraw works:

1. Clear the dirty box.
2. Redraw every primitive that touches the box, from any component, in the original paint order: window background, panel background, row, text, the shadow of the card next to it, a popover on top.
3. Pixels outside the box come from the kept texture.

So neighbours are redrawn only inside the box, with no per-component rules. Moving or removing something also works: the old spot's tiles change (it is gone) and the new spot's tiles change (it appeared).

**Example:** you hover a list row. Two tiles get a new highlight, so the box is about 600 × 64 px. Inside it, RustUI redraws the panel background, the highlight, the row's text, and the edge of the row above where it crosses the box.

Where to add more sophistication:

- **Several boxes instead of one.** A blinking caret at the top and a clock at the bottom today make one box covering everything between them. A few separate boxes (Zed caps it at 8) fix that.
- **Use GPUI Fast's records.** Views that GPUI Fast reused unchanged cannot have changed pixels, so their tiles need no new fingerprint. This saves CPU.
- **Blur and shadows:** their reach must be counted in their bounds. The tile code already does this for shadows.

### G3 — Scroll shift

Picture a log panel that auto-scrolls. Each new line pushes all the text up by 20 px. To G2, every tile in the panel changed, so it would redraw the whole panel, although the pixels are the same, just 20 px higher.

G3 sees this case: the same primitives, all moved by the same whole number of pixels, inside one clip. Then it:

1. Copies the panel's old pixels 20 px up inside the kept texture. A GPU copy is very cheap.
2. Draws only the new 20 px strip at the bottom, plus anything that did not move (panel header, scrollbar).

That turns "redraw a 600 × 800 panel" into "redraw 600 × 20". It needs whole-pixel moves: a 20.5 px move would blur the pixels, so it falls back to G2. GPUI Fast already does exactly this on Windows (software drawing only); G3 brings it to Metal. This is the piece that makes append-only panels (logs, timelines, chat lists) cheap.

### G4 — Drag on its own layer

Upstream GPUI draws one scene into one layer. GPUI Fast added **window composition** (ported from Zed PR #62379) so web views can sit inside a GPUI window. It stacks several layers, and the macOS window server combines them:

- **Front — overlay layer:** popovers, menus, tooltips, the dragged item
- **Middle — native views:** for example a WKWebView
- **Back — base layer:** your root view

GPUI Fast's `window.rs` already marks "base starts here" before painting the root view, and "overlay starts here" before deferred draws and the drag element. Two catches: composition is opt-in per window, and the scene is only really split into two layers when a native view exists. Otherwise everything goes into the base layer.

G4 is a small patch: enable composition for RustUI windows and also split while a drag is active. During a drag:

- The base layer usually does not change, so G1 skips it; if a drop target highlights, G2 redraws a small box.
- Only the overlay layer, which holds just the dragged item, is redrawn.
- macOS combines the two layers, which is cheap.

### G4 options, by case

The overlay layer alone always puts the dragged item on top, like GPUI's built-in drag preview. That is wrong when the design needs the item to keep its depth: drag A (zIndex 1) toward B (zIndex 2), and part of A should slide under B. So G4 offers one option per case. The developer picks the style; RustUI picks the cheapest correct method inside.

| Case | Developer picks | How RustUI draws it | Cost per frame |
| --- | --- | --- | --- |
| Drag ghost above everything (file to a folder, tab to another pane) | `DragStyle::Floating` | Dragged item on the overlay layer; base layer skipped (G1) | Redraw the small overlay item only |
| Item keeps its depth and slides under higher items (A under B) | `DragStyle::InPlace` | **Move in place:** A stays in the scene at its own zIndex and is painted at its new spot each frame; G2 redraws A's old spot plus new spot, in paint order, so B covers A correctly | Small box, e.g. about 210 × 100 px for a 200 × 100 item moving 10 px |
| Same as above, but the box gets big (a large item, a big window) | `DragStyle::InPlace` (no change) | **Layer sandwich**, chosen by RustUI: at drag start, split into 3 layers by paint order — everything before A, A alone, everything after A (B included, see-through elsewhere). Move only A's layer; merge back on drop | Zero redraw while moving; one split frame at start; 3 window-sized textures during the drag |
| Drop target reacts (B highlights) | any style | G2 redraws a small box on the layer that holds B | Small box |
| Drag over a native view (WKWebView) | `DragStyle::Floating` | Overlay layer sits above native views, so the item stays visible | Same as Floating |
| Animation that moves, fades or scales, look unchanged (sheet slide, toast, popover fade) | `LayerHint::Auto` or `LayerHint::Promote` | Item promoted to its own layer while it animates; only the layer's position or opacity changes; merged back at the end | Zero redraw |
| Animation whose pixels change (path spinner, growing progress bar, counter) | nothing | G2 redraws the small box around it | Small box |

**Rules for RustUI's inside choice:**

- `InPlace` starts with **move in place**. It switches to the **layer sandwich** only when the dirty box is over ¼ of the window, the case where a full box redraw costs more than the split.
- `LayerHint::Auto` promotes only for animations of position, opacity or scale on an item with its own solid background. `LayerHint::Never` turns promotion off for that item.
- A promoted item or sandwich layer is merged back as soon as the drag or animation ends, so memory returns to one texture.
- Every option must give the same pixels as a full redraw: checked by the Verify switch and the pixel tests.

**What the developer writes:**

```rust
// File dragged onto a folder: ghost above everything
div().on_drag(file, |f, _, _, cx| cx.new(|_| f.preview()))
    .drag_style(DragStyle::Floating);

// Card on a board: keeps its depth, slides under higher cards
card().draggable().drag_style(DragStyle::InPlace);

// Sheet sliding in: let RustUI promote it while it moves
sheet().layer_hint(LayerHint::Auto);
```

These API names are proposals; they do not exist in RustUI or GPUI today. GPUI only has the floating drag preview, so `InPlace` and `LayerHint` are new RustUI features.

**Idea to test later:** for `Floating`, if the dragged item looks the same every frame, move the overlay layer's position instead of redrawing it. Not yet confirmed to work with GPUI Fast's overlay as built.

### Text sharpness on layers

On macOS, layers never make RustUI text less sharp; on Windows and Linux they can, so layered items there need a solid background.

**Subpixel text.** Each screen pixel is three thin strips: red, green, blue. Subpixel smoothing lights each strip separately, so letter edges can sit between pixels and small text looks sharper. Windows calls this ClearType.

**Why it needs the background.** Subpixel smoothing mixes the text colour with the colour behind it, strip by strip. Black text on a white card gets edge values that only look right over white. On a see-through layer, the GPU does not know what macOS or the system will place behind it later, so subpixel smoothing cannot be used and the text falls back to normal smoothing, slightly thinner.

**macOS: no problem.** RustUI's macOS code returns `false` from `is_subpixel_rendering_supported()`, and GPUI Fast does the same. Apple dropped subpixel text in macOS 10.14. All RustUI text on macOS already uses normal smoothing, so moving it to another layer changes nothing.

**Windows and Linux: later.** GPUI can use subpixel text there, only in opaque windows. A layered item should either have its own solid background, so its text keeps subpixel smoothing, or use normal smoothing while it animates and switch back after it merges into the base layer. This is why `LayerHint::Auto` promotes only items with their own solid background.

## Frame pacing modes

Developers and users choose how RustUI trades smoothness against battery, through three modes. Every mode shows exactly the same pictures: modes change only when frames are drawn, never what is drawn, so no mode can cause a visual bug.

| Mode | What it does | Good for |
| --- | --- | --- |
| **Battery saver** | No extra pictures, never asks for 120 Hz. The screen slows down quickly. | Laptop on battery; simple tools |
| **Balanced** (default) | Keeps the screen fast for 1 s after input, using cheap copies (G1). Asks for 120 Hz only while the app is being used. | Most apps |
| **Smooth** | Asks for 120 Hz the whole time the window is in front. Keeps the screen fast for 3 s after input. | Editors, drawing apps, Chorus's live views |

**Who decides** (the higher one wins):

1. **Debug switch:** an environment variable, `RUSTUI_FRAME_PACING=smooth`, for testing only.
2. **macOS Low Power Mode:** always forces Battery saver. GPUI already reads the power state.
3. **The user:** picks a mode in the app's settings, if the developer allows it.
4. **The developer:** sets the app's default mode.

**What the developer writes:**

```rust
// Default for the whole app
App::new().frame_pacing(FramePacing::Balanced);

// Let the user change it, e.g. from a settings panel
cx.set_frame_pacing(FramePacing::Smooth);

// Advanced: exact values
cx.set_frame_pacing(FramePacing::Custom {
    keep_fast_after_input: Duration::from_secs(2),
    ask_for_120hz: AskFor120Hz::WhileInput,
});
```

**Example in Chorus:** Balanced is the default. A user who watches live agent runs all day switches to Smooth in Settings. When the MacBook enters Low Power Mode, RustUI drops to Battery saver on its own, and returns to Smooth when it ends.

**Damage tracking gets the same kind of switch,** mostly for developers:

| Setting | What it does |
| --- | --- |
| **On** (default) | Skip, copy or partial redraw, whichever is cheapest |
| **Off** | Always redraw the whole window, to rule damage tracking in or out |
| **Verify** | Draw both ways and report any pixel difference; slow, testing only |

## Order of work

Finish F0 and F first, then build G in five steps, each one shippable alone and each behind its own switch. Every step is split into tickets of at most two hours, as the roadmap requires, and every change lands as a patch.

**Before G (already planned)**

- **F0:** switch the base to GPUI Fast on an integration branch, rebase the 4 failing patches, run all matrices. Adopt only if the criteria pass.
- **F:** turn on retained views and scroll layers; audit RustUI render paths for state read without `cx.notify()`; check with `GPUI_VIEW_RETENTION=0` when anything looks stale.

**Stage G on GPUI Fast (macOS, Metal)**

1. **G0 — measure and prove.** Add GPU time per present (Metal command buffer GPU start/end times) and counters for presents: skipped, copied, partial, full. ## Verification and measurement

The rule is GPUI Fast's: the frame drawn from scratch is the specification. A partial frame passes only if its pixels equal a full redraw, byte for byte.

| Check | What it proves | Taken from |
| --- | --- | --- |
| Pixel test per frame mode | Skip, Copy, Partial and scroll-shift each equal a full draw on headless Metal | Havunen, Hexpy |
| Magenta pre-fill | Damaged pixels start magenta, so any pixel the partial path forgot shows up | Finityno |
| Random-history oracle | Random hovers, edits, appends, scrolls and drags; every frame compared with a full redraw | GPUI Fast oracle tests |
| Path-actually-ran assert | Each test fails if the partial path was declined, so it cannot pass by always drawing in full | Hexpy, GPUI Fast |
| `RUSTUI_DAMAGE_VERIFY=1` | Same comparison in a real app on the owner's Mac; logs the first mismatch with its tile | New |
| `RUSTUI_DAMAGE=0` | Turns all of G off at runtime, to rule it in or out | Zed flags, `GPUI_VIEW_RETENTION=0` |
| Patch checks | Each G patch has `--verify`, `--apply`, `--reverse` with exact hashes, like the current stack | RustUI `patches/` |

Acceptance per step: no pixel mismatch in any test; GPU time per present falls on its target workload; CPU time per frame does not rise by more than 3% on the F0 workloads (hashing tiles costs CPU). Hold each switch off by default until the owner's macOS check passes, then turn it on.

## Risks and open questions

- **Stale pixels.** A wrong damage box leaves old pixels on screen. Mitigation: the byte-identical tests, the verify switch, and every edge case (atlas, filters, surfaces, resize, scale) falls back to a full redraw.
- **Memory.** One retained texture per window: about 30 MB for a 3456 × 2168 window at 4 bytes a pixel. Havunen's budget (two 4K targets per device) caps it; over budget means full redraw, not failure.
- **Hashing cost.** Tile hashing runs on every frame on the CPU. Measure it in G0; GPUI Fast's retained views cut CPU so far that this should stay small, but it must be checked.
- **Scroll layers and damage meet.** A scroll-layer frame composites tile sprites over the whole viewport, so G2 sees every tile changed. G3 (scroll shift) is what fixes that; until G3 lands, scrolling gets no GPU win.
- **Transparent windows.** A translucent window blends with the desktop behind it. The retained texture must keep alpha exactly; test with a translucent RustUI window.
- **Upstream drift.** Havunen's code targets gpui-ce and the `metal` crate; GPUI Fast uses `objc2-metal` and changes often. Keep the port in new files with small hooks, as GPUI Fast's `check-upstream` script enforces for its own code.
- **Open:** whether Havunen #29 and Zed #62455 are merged could not be confirmed; neither changes the plan.
- **Open:** the drag-overlay step replaces the earlier plan of a hand-built wgpu surface via `raw_window_handle`. Confirm before G4 tickets are written.
- **Open:** turn on G by default per step, or all at once after G3?
