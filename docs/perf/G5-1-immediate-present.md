# G5-1 — input-tick presentation

**Owner accepted G5-1 on November 22, 2026, with quiet-machine confirmation deferred.** The acquisition gate is **no nextDrawable call > 2 ms (¼ refresh at 120 Hz) inside measured windows; all >1 ms calls listed with path, in-flight count and time since detach**. The original 1 ms gate failed: **18/27,025 calls, 16 warmup and two measured, maximum 1.297 ms, with spare tracked capacity**. The accepted measurements were **measured on a loaded machine** (23.12–41.36% background). Those historical results remain below; the revised gate does not relabel the old failure. All runtime switches remain off by default.

## Implementation

The hashed reversible candidate is `patches/candidate-fast-latency/gpui-fast-immediate-present-v1-fast`. It queues work on GPUI's existing foreground executor after input effects settle, preserves dirty state while drawable capacity is unavailable, and checks `in_flight < maximumDrawableCount` again at acquisition. Presented handlers retire unique acquisition lifetimes, including reused drawable pointers, and wake pending work. Live resize uses the existing synchronous path. Vendor and owned GPUI sources change only through the patch applier; owned crates are regenerated by script. No candidate is promoted.

`GPUI_FAST_IMMEDIATE_PRESENT=1` enables the behavior. Its default is off. `GPUI_FAST_IMMEDIATE_HOLD_MS` defaults to 250 only when the master is enabled; zero disables the hold. Hold requires consecutive inputs strictly less than 100 ms apart; a first input or gap of at least 100 ms clears it. Scheduled demand during hold uses the same immediate queue. CATransaction post-fix comparison pairs were dropped by owner decision after the common-endpoint comparison showed no AppKit advantage.

macOS rejects explicit nextDrawable acquisition while a CAMetalDisplayLink is attached. Immediate presentation detaches that source. A later asynchronous notification must still wake the window after hold and pending presents end: the macOS frame waker coalesces a deferred source-restoration task on the existing foreground executor. The task captures weak window/source references, avoiding a retain cycle and avoiding a window-state lock inside invalidation. An attached source is simply unpaused. Normal disabled behavior follows the existing waker path.

The optional `RUSTUI_G5_ASYNC_WAKE=1` bare-reference workload checks a key edit followed one second later by an asynchronous notify, without another input. It is a correctness workload, not a latency benchmark.

## Measurement protocol

One pinned release build per runtime revision; five matched off/on pairs per rate, alternating off→on, on→off, off→on, on→off, off→on; 60 seconds after normal warmup. Immediate mode is on in both hold arms, with hold duration 0/250 ms. Damage is off and buffered logging flags are identical. No compilation, tests or profiling overlap timing. Process CPU uses getrusage user+system per attempted present and the P verdict rule in [MEASUREMENT_RULES.md](MEASUREMENT_RULES.md). NEUTRAL and INCONCLUSIVE are not gains.

The explicit owner CPU-gate bypass uses `RUSTUI_G5_BACKGROUND_LIMIT=none`; default tooling remains 10%. Every capture logs raw top -l 1, corrected start/end background CPU and the top five processes, and is labeled measured on a loaded machine. Raw captures and machine-control bookkeeping remain local and are not committed. Folder exclusions and undo instructions are in [Machine setup](MEASUREMENT_RULES.md#machine-setup). A quiet-machine confirmation is deferred.

MTLDrawable.presentedTime is the Metal display endpoint. AppKit NSTextView has no drawable, so both common-method arms use the same version barcode and ScreenCaptureKit WindowServer displayTime. That endpoint remains separately labeled; it is not substituted for presentedTime. The pixel observer records transitions including returns to old versions. Analysis uses all transitions for monotonicity and the actual final displayed version, with separate distinct-version bookkeeping for latency and coverage. Regression tests explicitly require `1 → 2 → 1` and a return to version zero to fail monotonicity.

The original 5.849541 ms acquisition used the immediate path, with the display link detached and old post-call count 0/3, 39,930.574 ms since detach. Its physical cause is not established. A capacity counter is not a guarantee that Metal acquisition cannot wait; all call durations remain disclosed.

## Owner decision and verification

The owner accepted the loaded-machine results with quiet confirmation deferred. Both measured acquisition outliers, 1.192708 and 1.120417 ms, satisfy the revised measured-window 2 ms gate. The old 1 ms failure remains explicit. Sparse p95 stays within one 8.333 ms refresh of hold-off; fast held p95 25.937 ms is below 39.560 ms. Final text/version checks passed; CPU was INCONCLUSIVE at both rates. This is ticket acceptance, not visual approval.

The review corrections add asynchronous detached-source restoration, preserve pixel version transitions, and remove transient session history from this document. Focused verification passed 17 Python tests, nine compiled Rust state tests and the native Swift transition-filter test. `scripts/check.sh` passed all seven groups: 1,868 passed and seven ignored, 1,875 total. Source verification passed 712 script tests and its source gates. Both damage and latency stack checks passed exact postimages. The asynchronous display-time limitation remains stated above. Source CI must be green on the final commit, with every review comment answered, before merge. PR #171 targets g5-integration only; no main merge or default-on change is authorized.
